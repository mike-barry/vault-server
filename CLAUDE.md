# CLAUDE.md - Vault Access Rewrite Build

This repository is a from-scratch build of the vault access layer, its tool layer, and two front-ends over them, specified entirely by the documents in `docs/spec/`.

**Read `docs/Brief-Vault-Access-Build.md` first.** It is the single entry point: what is being built, which documents specify it, which code is retained and already correct, and which constraints are deliberate. Everything else in `docs/spec/` is reached through it.

## Constraints

- **This repo has no access to the knowledge vault, and must not seek one.** The as-built documentation of the system being replaced is deliberately out of reach. Do not look for it, do not ask for excerpts of it, and do not reconstruct it from memory of another session. A redesign grounded in documentation of the old system inherits the old system's shape, which is the one outcome this build exists to avoid.
- **Most of this repo is retained code and is already correct.** Authentication and authorization, the scope primitives, health, logging, configuration loading, host wiring, and the script-loading framework all carry forward. Read them, call them, and do not reimplement or refactor them. The brief lists what is retained and what was deleted.
- **The deleted implementation is not recoverable, by design.** Git history was restarted. There is nothing to check the specifications against, which is what makes them the specification rather than a summary.
- **Gaps escalate; they are not resolved locally.** On a question the specs cannot answer, stop that thread and raise it with the operator rather than deciding from judgment. Only an agreed escalation is written to `docs/Questions.md`, and the answer returns as an amended spec. Clear the entry once the answer is incorporated into both the specs and the code.
- **Design decisions land where the design is, not in a separate log.** `docs/design/README.md` is the convention: a design document's `What This Closes` section carries every point the specs left open and the rule chosen, with the rejected alternative only where it is attractive enough that someone would try it. A decision with a code site is a comment there, written as a constraint rather than a story. Git history carries the rest, and the commit message is where a change explains itself. Nothing outside this repo observed the build, so a decision recorded nowhere is one nobody can review - but a central log of them is read by nobody and duplicates what the design document and the commit already say.
- **Comments are written in the register of MSDN documentation.** A summary opens with a verb phrase and states plainly what the thing does, and a documented member documents every one of its parameters - `CS1573` enforces that at build time on the three `src/` projects. Justification appears only where a constraint is not self-evident from the code and a maintainer would otherwise break it, as one sentence stated as fact rather than argued; a longer caution goes in `<remarks>`. Comments never reference the spec or design documents, which are archived at cutover: a fact worth keeping is stated in the comment itself, including what it was measured or agreed against and what changing it breaks.
- **Where retained code and a spec conflict, the spec wins and the retained code moves.** The brief says a retained component that looks wrong should be raised, because a misread requirement is the likelier explanation. That presumption holds for a component whose subject the specs do not cover. Where a spec does cover it, the specs are the specification: propose the change to the retained code and get approval, rather than escalating it as a possible defect in the bundle.
- **`docs/Plan.md` holds the working plan.** Read it at the start of a session and say which step is in play. It is the build's own plan and is meant to be revised as the work is understood, with changes proposed to the operator rather than made silently.
- **`docs/Sidequests.md` holds agreed work that does not block the build.** Real problems found in passing - a portability defect, a hygiene fix - worth doing but not now. **Only the operator writes to it.** Propose promotion when you find something that fits and say what it costs to leave; do not add an entry yourself, or the file stops being a list of agreed work and becomes somewhere to shed anything inconvenient. Something that blocks a step belongs in the plan, and something the specs cannot answer is an escalation.
