# CLAUDE.md - Vault Access Layer

This repository holds the vault access layer, its tool layer, and two front-ends over them. The code is built and its suite passes. What remains is a full code review, a conformance audit of the code against `docs/spec/` and `docs/design/`, a comment sweep, and cutover to the canonical `vault-server` repository.

**`docs/Brief-Vault-Access-Build.md` is the entry point to `docs/`.** It says which documents specify what, which code carried forward, and which constraints are deliberate. Everything in `docs/spec/` is reached through it.

## Constraints

- **`docs/spec/` is the specification, and it stays live until cutover.** No implementation of the old system is reachable from here, so nothing else states what this system is required to do and nothing can check a spec from inside this repository. A change to behavior amends the spec and rewrites the affected design text in the same commit; a stale spec is undetectable here and leaves the archived record describing something that was never decided.
- **This repo has no access to the knowledge vault, and must not seek one.** The as-built documentation of the system being replaced is deliberately out of reach. Do not look for it, do not ask for excerpts of it, and do not reconstruct it from memory of another session. Code is judged against the specs; a judgment grounded in the old system's documentation reintroduces the old system's shape, which is the one outcome this work exists to avoid.
- **Most of this repo is code that carried forward and is already correct.** Authentication and authorization, the scope primitives, health, logging, configuration loading, host wiring, and the script-loading framework. Read them, call them, and do not reimplement or refactor them. The brief lists what carried forward and what was deleted.
- **Where retained code and a spec conflict, the spec wins and the retained code moves.** The brief says a retained component that looks wrong should be raised, because a misread requirement is the likelier explanation. That presumption holds for a component whose subject the specs do not cover. Where a spec does cover it, the specs are the specification: propose the change to the retained code and get approval, rather than escalating it as a possible defect in the bundle.
- **Gaps escalate; they are not resolved locally.** On a question the specs cannot answer, stop that thread and raise it with the operator rather than deciding from judgment. Only an agreed escalation is written to `docs/Questions.md`, and the answer returns as an amended spec. Clear the entry once the answer is incorporated into both the specs and the code.
- **Design decisions land where the design is, not in a separate log.** `docs/design/README.md` is the convention: a design document's `What This Closes` section carries every point the specs left open and the rule chosen, with the rejected alternative only where it is attractive enough that someone would try it. A decision with a code site is a comment there, written as a constraint rather than a story. Git history carries the rest, and the commit message is where a change explains itself. A decision recorded nowhere is one nobody can review - but a central log of them is read by nobody and duplicates what the design document and the commit already say.
- **Comments are written in the register of MSDN documentation, and `conventions/Code-Comments.md` is the standard.** Read it before writing or modifying a comment; `conventions/Comment-Sweep.md` covers running a sweep over the whole repository. Three rules hold whether or not that document has been read. A summary opens with a verb phrase and says plainly what the thing does. A documented member documents every one of its parameters - `CS1573` enforces that at build time on the three `src/` projects. A comment stands on its own: it never references the spec or design documents, which are archived at cutover, and it never leans on a compressed idiom or a fact stated elsewhere, so a reader who has opened nothing but the file in front of them understands it on first read. A fact worth keeping is stated in the comment itself, including what it was measured or agreed against and what changing it breaks.
- **`conventions/Unit-Tests.md` is the standard for the tests.** A test asserts a behaviour a caller can observe. Read it before adding or changing one.
- **`conventions/` outlives this work and does not archive with `docs/`.** The specifications, the design documents, and the working files are archived at cutover; the comment and test standards govern the code and travel with it into the canonical repository.
- **`docs/Plan.md` holds the working plan.** Read it at the start of a session and say which step is in play. It is meant to be revised as the work is understood, with changes proposed to the operator rather than made silently.
- **`docs/Sidequests.md` holds agreed work that does not block the remaining steps.** Real problems found in passing - a portability defect, a hygiene fix - worth doing but not now. **Only the operator writes to it.** Propose promotion when you find something that fits and say what it costs to leave; do not add an entry yourself, or the file stops being a list of agreed work and becomes somewhere to shed anything inconvenient. Something that blocks a step belongs in the plan, and something the specs cannot answer is an escalation.
