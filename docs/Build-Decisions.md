# Build Decisions

In-flight judgment calls made during the build where the specs and design left a small gap and the obvious solution was taken rather than stopping. A review queue for the operator: each entry says what was decided and why it follows from what is written. An entry that turns out to be a real design decision migrates to its design document's `What This Closes` or a comment at the code site, and comes out of here. Ratified entries the code already documents can simply be deleted.

## Core access layer, slice: path types and VaultAccess

- **Refusal order is malformed → perimeter → scope.** The perimeter binds "whatever its scope" (`Design-Core-Access-Layer.md:Refusals`), so it must be decided before scope; text that is not a path at all cannot be classified by either. Caller-visible only in which refusal a doubly-bad path gets.
- **`Malformed` carries a reason string** taken from `ScopePath.Normalize`'s exception message (parameter suffix stripped). Oracle-safe: the message derives entirely from the caller's own text.
- **`Admits` throws on a candidate from another vault** rather than answering false. A cross-vault candidate is a layer defect, not a scope answer — same posture as `Grant.ScopeIn` on a missing vault (fail as on an upstream defect, never interpret as permission).
- **`Unavailable` resolutions canonicalize the name too**; only `Unknown` echoes the caller's spelling, it being the only spelling that exists. The spec's canonical-name rule speaks of resolution generally, and a skipped vault is configured, so a canonical spelling exists.
- **`VaultPath.TryCreate` is public.** Containment is not admission — a `VaultPath` reaches no operation without passing `VaultAccess` — and the census/enumeration slices need the producer.

## Core access layer, slice: the file primitives

- **The primitives are static members on `VaultFiles`, not members on `VaultAccess`.** A primitive's authority is the type of the path it is handed, so there is no per-call state to hold; enumeration and search sit on `VaultAccess` because they must be *filtered* by a scope, which these are not. It also leaves the vault-wide pass free to reach the same mechanics from its own object rather than through the scoped one.
- **`Replace` refuses a target that is not there**, from `FileMode.Truncate` rather than a probe. The specs say "replace an existing note's content wholesale" and make creation the other form; a replace that created would make the two forms one, and only the creating form checks the grammar.
- **Folder creation establishes its parent with a check.** The one probe in the slice, and unavoidable: the platform offers no non-recursive directory creation, so without it the call would materialize every missing folder above the target. The window is a parent deleted between the check and the create. Every other refusal here comes from the attempt.
- **A folder already there is not an error.** Directory creation is idempotent on every platform and cannot report the difference without a second probe, and no spec asks for the refusal.
- **A missing parent for a path directly under the root is `Failed`, not `MissingParent`.** The root is a vault rather than a path and has no vault-relative rendering; a root that is not there is what vault resolution answers `Unavailable` for.
- **Move passes `overwrite: true` only when the destination is the source under another spelling.** .NET's non-overwrite move pre-checks the destination on Unix, so a case-only rename would otherwise refuse its own target on a case-insensitive filesystem. No other occupant is ever replaced.
- **Move relocates a file; a folder source answers `SourceMissing`.** Each operation states what it expects and fails on the other, and the folder relocation the tool spec composes needs a decision this slice does not have to make. Flagged rather than assumed — see the report.
- **Removing a file is an open with delete-on-close.** `File.Delete` succeeds silently on a file that was never there, so it cannot produce the classification removal owes; the open fails when nothing is there and the entry is unlinked as the handle closes.
- **"Already exists" and "not empty" are recognized from the platform's error code.** Both arrive as a plain `IOException`, shared with sharing conflicts and device errors, so the exception type alone would collapse a refusal the specs require to be distinguishable.
- **A failure reason renders every location it names vault-relative.** The platform puts the absolute path in its message, and a reason carrying one would take an absolute path out of the layer.
- **One `WriteOutcome` across replacing, creating and folder creation.** Their refusals are the same refusals; each operation's documentation says which cases it produces. Three near-identical hierarchies buy exhaustiveness at the cost of the reader.
- **LF normalization happens in the write primitive.** `Spec-Frontmatter-Substrate.md:Preservation Invariants` normalizes "on entry, not on the way out", but that governs the substrate's own before-and-after guard; the composing seam is where the design states terminators, and stating them anywhere else makes the rule one every caller must remember.
- **The note extension is matched ordinally.** `.MD` is not a note name: this grammar is checked only on a name being brought into existence, where one spelling is the whole point.
- **`VaultPath.Absolute` and `ParentValue` are internal.** The primitives compose root and segments; nothing outside the layer sees an absolute path.

## Core access layer, slice: enumeration and content search

- **One outcome hierarchy, `SearchOutcome<T>`, across both enumeration surfaces and all three search granularities.** The specs state the same four outcomes once, for both; a second hierarchy would restate them and let the two drift. A pattern-bearing enumeration is itself a name-and-path search (`Spec-Access-Layer-Capabilities.md:Enumeration`).
- **Content search answers notes only**, filtered by the same predicate note enumeration uses. `Spec-Access-Layer-Capabilities.md:Content Search` says "over note content", and `Spec-Tool-Capabilities.md:Enumeration Domains` places search in the note domain beside discovery. The layer offers one search domain because the specs name one.
- **A count is matching lines, not matches** (`--count`, not `--count-matches`), so a file's number agrees with what the line granularity returns for the same search. The specs say "a count per file" and settle no further.
- **A caller's bad pattern is told from a failure during the search by whether the engine produced output**, not by reading its message. It refuses a malformed glob or regex before walking anything, so such a run is silent on both streams but one; every other failure arrives with whatever the run had already emitted. The three search granularities therefore ask for a completion marker they do not otherwise need - the JSON summary event, and `--stats` for the two cheap shapes - so that a run which matched nothing and also failed on a file is not read as a refusal.
- **Enumeration carries a known classification edge.** `--stats` is silently ignored with `--files` (verified against rg 15.2.0), so enumeration has no completion marker: a walk failure that emits zero paths before erroring - in practice an unreadable vault root - classifies as `BadPattern` rather than `Failed`. The engine's text is carried either way; recovering the distinction from message text is the fragile form the specs reject, so the edge is accepted and named here.
- **An unreadable-file failure names the entry the engine attributed it to**, taken from its `rg: <path>: <reason>` diagnostic and confirmed by that text resolving as a path in this vault. A diagnostic naming no entry is operational instead, which is what gives the fourth outcome a case of its own.
- **Anything on the error stream fails the call whole**, whatever the exit code. A partial answer from a search that could not read something is the wrong answer the load-bearing semantic exists to prevent.
- **Every invocation names its operand explicitly.** The engine searches standard input when nothing is named and standard input is redirected, which it always is for a child process - the answer would be a search of nothing, reported as an empty result.
- **`--no-config`**, because the engine otherwise takes options from a file named by an environment variable. Nothing the layer depends on comes from ambient state.
- **An unhanded engine location means `rg` on `PATH`.** The retained host's fallback for an unset `RipgrepPath`, and a constant rather than something the layer reads from its environment.
- **The engine is driven synchronously.** The tool surface above is synchronous because the mutex hold cannot cross a suspension point, so an asynchronous layer underneath would be blocked on at every call site anyway.
- **The markdown test is case-insensitive**, unlike the note extension `VaultFiles.Create` checks ordinally. Enumeration and search must reach what is already on disk, where names are not grammar-checked; creation brings one name into existence, where one spelling is the whole point.

## Core access layer, slice: wikilinks and the vault-wide pass

- **An occurrence's extents index the text they were recognized in**, character offsets rather than UTF-8 byte offsets. The requirement is that a consumer overwrite a range and never parse the note (`Spec-Access-Layer-Capabilities.md:Wikilink Grammar And Resolution`); the unit follows from what the layer's read hands out, which is decoded text, and a byte offset would make every consumer convert before it could use one.
- **The target extent stops at the first `|` or `#`.** An alias and a subpath are decorations a link carries, and only the target portion is rewritten (`Spec-Tool-Capabilities.md:Wikilink Maintenance`). A target extent that swallowed `#Design` would match no path, which is the silent-failure direction matching exists to avoid.
- **Padding around the target is outside its extent**, so what the extent covers is exactly the name and a rewrite of `[[ Widget | Alias]]` leaves the spacing.
- **A link naming nothing is not an occurrence** - `[[#Heading]]`, `[[|Alias]]`, `[[  ]]`. It references no file, and a zero-length target extent is one a substitution would insert into rather than write over.
- **The grammar knows no markdown structure, so a wikilink inside a code fence is an occurrence.** Nothing in the bundle says how the editor indexes fenced links. Tracking fences would mean parsing the note - the one thing every consumer here exists to avoid - and recognition runs over frontmatter as well as body, where fences do not apply. Being wrong this way over-reports to the census and rewrites a name inside a code sample; the other way silently misses a link.
- **A link's inner text holds no bracket and never crosses a line boundary.** The line rule is the spec's, and it is what keeps a substitution from creating or moving a frontmatter fence. The bracket rule is what lets `[[A[[B]]` resolve to the inner link rather than to a target no path matches.
- **Matching is case-insensitive throughout**, matching `VaultPath` equality and the scope semantics behind it: two spellings name one file.
- **The extension is the target's to omit, and only `.md` is.** The editor writes a note's target without an extension and every other file's with its own, so a final component matches a segment exactly or as that segment's stem when the segment is a note. `Diagram` therefore does not name `Attachments/Diagram.png`, since nothing in the target says what to restore.
- **`/` is the only separator a target is read with.** A target holding a backslash is a bare name containing one, and names nothing.
- **The tie-break compares `VaultPath.Value` ordinally.** `Spec-Obsidian-Link-Behavior.md` says vault-absolute, and vault-relative-from-root is what the layer holds - absolute paths never leave it, and the leading root is a constant across candidates either way.
- **Ranking validates its candidate set before sorting.** A candidate from another vault is a layer defect, and checking inside the comparison would surface it as whatever the sort wraps it in.
- **The vault-wide pass offers no creating write and no pattern.** It exists to rewrite what already links, over every note; creation is an operation whose own target is scope-checked normally, and a narrowed pass is a scoped enumeration under another name.
- **The pass leaves dot entries out and takes no switch for them.** No path under a dot-directory is reachable by the tool set at all, which is not a narrowing scope imposed (`Spec-Tool-Capabilities.md:Wikilink Maintenance` leaves out only dot-directories).
- **`VaultAccess.BypassingScope()` is the named call, and `VaultWidePass` has no public constructor.** The name states what is being bypassed rather than what it will be used for, so one grep finds every site; the constructor is what makes the call the only way in.

## Frontmatter surface, slice: the split, the tree, and the composer

- **`NoteSplit.Of` normalizes terminators itself, and `NoteSplit.Normalize` is public beside it.** `Spec-Frontmatter-Substrate.md:Preservation Invariants` puts normalization on entry, and the split is the entry every consumer of this surface passes through, so doing it anywhere else makes it a rule each caller remembers. The member is exposed because `BodyOffset` indexes the normalized content: an entry point that holds content across the before-and-after guard normalizes once and splices into that string. Normalization is idempotent, so doing both gives the same offsets as doing either.
- **A terminator is `\r\n`, matching `VaultFiles.Emit`.** A lone `\r` is left alone by both, so the substrate's entry seam and the storage seam agree on what a terminator is rather than one of them finding a byte the other left.
- **The parse is handed the block's text with a terminator restored.** The split hands over the text without the final inner line's one, which is where a block scalar reads its trailing newline from; parsing it as given rewrites `desc: |` as `desc: |-` on the first operation against a note nobody asked to reformat. The composer always terminates the block, so restoring it makes the two inverses. `InnerText` itself is unchanged - the facet is what the spec fixes, not what the parser is fed.
- **The parse answers three cases, `Parsed`/`Unparsable`/`NotAMapping`, and never a null tree.** The write path refuses the last two for distinct reasons (`Design-Frontmatter-Surface.md:Refusals And Violations`), so collapsing them would lose a refusal the design names; the tolerant read collapses both to an empty tree, which is the difference between the two sides.
- **Key membership is `OrdinalIgnoreCase` throughout** - lookup, canonicalization, shape, the reads, and entry field names. One constant, matching how the rest of the layer compares names.
- **`Canonicalize` takes the declared spelling as an argument.** The tree knows no vocabulary and cannot reach a declaration; passing it in is what lets the same member serve both halves of the rule - the tree's spelling where the key is present, the declaration's where it is not.
- **The tree carries `Set` and `Remove` and nothing else that mutates.** They are what the operation vocabulary drives; entry-level manipulation is the operations' own, since it needs variants, identity, and anchors this type has no way to know about.
- **`ImplicitDocEnd` is internal.** Behaviour verbatim from `Spec-Vault-Access-Design.md:Frontmatter Emitter Settings`; the visibility is not, because a public decorator would put YamlDotNet's emitter types on this assembly's surface, against the rule that no caller holds a node.
- **`Emit` guarantees the block's text ends with a terminator**, so the closing fence gets its own line whatever the last value's style was.

## Frontmatter surface, slice: the registry, its loader, and the config lifts

- **The loader is pure of the sink; the cascade owns the reporting.** `FrontmatterRegistryLoader.Load` takes a path and answers a `RegistryState`, and `FrontmatterRegistries.Load` is what records Degraded - because the spec's degradation is *per vault* and only the cascade knows which vaults named a file. It also keeps one instance per file from recording one problem per vault that shares it.
- **A vault naming no `frontmatter_registry` is `Absent` with an empty path, and is recorded Degraded.** The three states are settled and a fourth for "never declared" would be one more case every consumer branches on for the same refusal. The empty path is what tells the two apart in the report: one names a file to fix, the other names none.
- **The declaration is resolved against the directory holding `vaults.json`,** not the vault root and not the process's working directory. The spec puts it beside the grant and op-class configuration at the same trust tier, and resolving it against the vault root would put the source of every key-level protection inside the thing it protects.
- **Constraint kinds are spelled `date`, `enum`, `charclass`, `wikilink`, `string`.** Three come from the registry spec's illustrative declaration; `enum` and `string` are named to match. The spelling is the file's surface, so it is stated here rather than left to a reader of the switch.
- **A date constraint's format defaults to `yyyy-MM-dd`** and is matched whole under the invariant culture. The illustrative `{ "kind": "date" }` carries no format, and ISO's calendar date is what the editor writes and what sorts correctly as text.
- **The character classes are a closed set of five** - `alpha`, `alnum`, `alpha-dash`, `alnum-dash`, `alnum-dash-space` - ASCII only. Only `alpha-dash` is named by the spec; the rest exist so the placeholder shape is usable without a new record per vault. A class admitting every Unicode letter bounds very little, which is the one thing this constraint is for.
- **An enumeration compares ordinally.** The declaration lists the exact text permitted, so a spelling that differs by case is a different value.
- **The wikilink constraint recognizes through `Wikilink.Recognize`** and requires the whole value to be one non-embedding occurrence. A second reading of what a link is would admit values the census cannot see; the embedding form is excluded because a declared field holding a link references a note.
- **`identity_match` is required wherever an identity is declared.** No default is right: a file identity compares as the filesystem resolves it and a line of prose compares exactly, and guessing either makes a scan and an operation disagree about whether an entry is already there.
- **Two scalar variants in one schema are refused**, on the same ground as two sharing a discriminating field: a bare value would match both, and matching two is a violation rather than a precedence rule to invent.
- **`version` is optional and must be 1 when present.** A declaration written against a later shape must not be read as this one; the fields such a version adds would hit the unrecognized-key refusal, but the ones it repurposes would not.
- **A `note` field is accepted on a key, a namespace, a variant and a field, and is carried as an init-only property** rather than a positional one, so the design's record shapes are unchanged. The spec permits the field explicitly; refusing it would be refusing something specified.
- **The parser de-duplicates `mutation_requires` by target and class, not by entry.** Two entries naming one target with two classes both survive, because contributions union and no entry can clear one another contributed.
- **`always_readable` with a `rule` target is refused.** A read floor is a set of path prefixes, and a structural rule is a shape rather than a place - the refusal states what `PathPolicy` could otherwise only silently drop.
- **Path policy's `mutation_requires` op class is checked against the op-class configuration at load, exactly as the registry's is.** Every authority named anywhere now validates against one registry, so `VaultConfigLoader` takes it as an argument and op-classes are first in the cascade for all four consumers rather than for two of them. An entry naming an undefined class is dropped and recorded Degraded like every other malformed entry, and its class is canonicalized to the registry's spelling on the way through. The known edge: when op-classes.json itself fails to load, every such entry drops against the empty registry - noisy, but the host is already refusing every request on the fatal above it, and the alternative is a second skip guard whose only reader is a host that has already stopped serving.

## Frontmatter surface, slice: the operations, the write path, the validator, and the projection

- **Three reasons and one rule join the design's enumerations**, each because a remedy the specs distinguish would otherwise be indistinguishable. `RefusalReason.WholesaleRemovalRefused`: the spec has a removal refused because the variant is not clearable wholesale, and the caller's next move is to name entries one at a time - nothing like the move after an identity that matched nothing. `RefusalReason.RegistryUnavailable`: the fail-closed seam raises in this vocabulary, and the error catalogue already carries `frontmatter_unavailable` for it. `ViolationRule.BlockWhereScalarDeclared`: the mirror of the compiled-in inline-value check, reported rather than refused because the validator reports on notes it did not write.
- **The validator reports an unparseable block rather than passing it over.** Tolerance is that one malformed note does not fail a whole-vault pass, not that the note is called valid. A silent pass would break the design's own rule that a note the validator passes is not one an operation refuses over the same key, and the sweeping consumer this return shape exists for is exactly the one that needs to see it. It is the single violation carrying no key.
- **Two note-dependent refusals are raised in the apply phase rather than the validate one**: whether the note's own field holds a block, and whether an identity or an anchor resolves. Operations are ordered and each sees the previous result, so deciding either up front would decide it against a tree an earlier operation has already changed. Both still precede every serialization, which is what the phase ordering protects.
- **A body-only write never parses the note's block.** The write path refuses a block nobody can parse because writing into one means guessing; a body write reads no key and composes no block, and refusing it would leave a malformed block unfixable from the body side. What keeps such a write off the frontmatter is the guard, not the parse.
- **The emptiness test binds addressing values, not every value.** An identity, a removal target, an anchor, a bare entry payload and a key are refused when empty - the additive and subtractive forms applying one test to the same argument. A scalar field's value is not: an empty string is a legitimate value under a string constraint, and what bounds it is the declared constraint.
- **A tab is refused with the other control characters.** The spec names line terminators as the exception, on the ground that the emitter handles them; a tab is not a terminator, and YAML cannot carry one as indentation at all.
- **Idempotence is keyed on declared identity, and "repetition is meaningful" holds where no identity is declared.** The two statements in `Spec-Frontmatter-Substrate.md:Semantics Every Operation Must Obey` read as conflicting for a variant that declares one - a second add differing only in a non-identity field is both "two entries" and "a pure no-op". The pure-no-op rule is stated twice and load-bearing, so it wins; repetition stays meaningful for a variant with no identity, such as a bare hint. Flagged rather than assumed - see the report.
- **An entry is addressed across the whole list, each candidate compared under its own variant's declared comparison.** One rule serves duplicate detection, removal and anchors, so the additive and subtractive forms cannot disagree about whether an entry is there.
- **A variant with no declared identity is addressable by nothing.** A scalar variant declares no fields, so the loader cannot give it an identity; such an entry is removable only by a wholesale clear, and every add of one appends. That follows from the declaration rather than from a rule here.
- **`AppliedOperations` is 0-based**, because it indexes the caller's own operation list. Entry positions reported to humans stay 1-based, which is a different coordinate with a different reader.
- **`FrontmatterChanged` is a byte answer and `ChangedKeys` is a meaning answer.** A reserialization that changed only quoting is not a changed key and does not deny a write, and it is still a changed facet, which is what a caller storing bytes needs to know. The no-op guarantee sits ahead of both: where no operation ran and the body did not change, the caller's own content comes back untouched rather than recomposed.
- **Path policy contributes nothing to a call that mutates nothing.** `mutation_requires` prices mutating a target, and a call that composes no change mutates none.
- **`PathPolicy.MutationRequires` is the one matcher, and it lives on `PathPolicy`.** An additive member on migrated code rather than a matcher in this namespace: `move` and `delete` consult the same entries at their own validate phases, and three implementations of "anchored, whole-segment, case-insensitive" are three answers. A path it cannot read throws rather than answering "no match", matching `VaultScope.Admits`.
- **The advertised vocabulary is a neutral record model, not a rendered schema document.** Which dialect carries it is the tool vocabulary's, and choosing one here would put that decision in the layer that must not know which front-end is asking. A variant's discriminating field is pinned by being required on its branch, which is what presence-based discrimination becomes in a client-facing schema.
- **The fail-closed seam is `RegistryState.Require()`.** The write path takes a loaded registry, so the refusal belongs where a caller obtains one; the alternative - every write site remembering to match on `Loaded` first - is a convention rather than a guarantee. The projection takes the state instead and answers an empty vocabulary, since advertising was never permission.
- **`VaultAccess` implements `IKeyAuthority` explicitly**, so the interface reaches the surface without widening what the vault type advertises, and it translates its own `AuthorityRefusal` into the frontmatter denial - which names the changed key set rather than the op class that failed, because what a caller lacks is information about its grant.
